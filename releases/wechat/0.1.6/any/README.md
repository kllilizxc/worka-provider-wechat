# Worka WeChat provider

This independent module ships with Worka and registers the `worka-wechat` extension. It imports only Node built-ins and the public `@realiz3r/worka/host` contract. It can be extracted into a separately distributed package without importing the Worka application or another provider.

The current local reader supports macOS arm64 and WeChat 4.x. It is a local database reader, not a Tencent API integration. It never sends WeChat messages.

## What is implemented

`registerWeChatProvider(host, config?)` registers `extension.worka-wechat.*` resources and one host-owned `worka-wechat.messages` synchronizer. Distribution assets belong next to the compiled entry: `runtime/` and `bridge/`. An assembler can instead pass their absolute parent directory as `assetsRoot`.

| Local deployment setting | Meaning |
| --- | --- |
| `assetsRoot` | Absolute directory containing this package's runtime installer/receipt verifier and bridge. Defaults to the compiled entry's directory. |
| `runtimeUrl` | Optional deployment override for the pinned runtime archive. Normal installs use the archive shipped beside this provider. |
| `runtimeArchive` | Optional local archive override, verified against the same pinned hash. Normal installs do not require a user-supplied path. |
| `runtimeConfig` | An explicitly selected existing runtime configuration. Used read-only until preparation writes this provider's own profile metadata. |
| `keyConfig` | An explicitly selected existing key configuration. Keys are referenced and checked, never copied or synthesized. |

Managed configuration/cache lives under the absolute path `host.dataRoot/providers/worka-wechat`; downloaded immutable components live under `host.dataRoot/components/worka-wechat`. No default path overlaps the old `wechat` provider. First registration reads only the new private state and registers resources; it never starts key extraction, installs the runtime or reads WeChat. Synchronization starts only after an authorized check has joined a note, including restoration of that previous authorization after restart.

The account owns its cache and reading process. Each authorized note joins that connection, selects its own chats, and controls its own synchronization and event subscription. A second note does not replace the first note. Concurrent installation, connection verification, and reads of the same chat share their current tasks. Disconnecting or pausing one consumer preserves the other consumers and account cache. An account change never writes the new account's messages into the old account's cache.

The old `wechat` extension may remain installed while this module registers `worka-wechat`; neither registration replaces the other. This is migration isolation, not a compatibility bridge. The module never scans or copies the old provider's cache or runtime configuration. A one-time explicit handoff can preserve the earlier single-note cache: stop Worka and the old provider, identify its actual absolute state path, preserve a copy, and copy that selected `connection.json` into the new provider's private directory before startup. Do not edit either live store behind its writer. The loader recognizes that file's old data shape, turns its old owner into a consumer, and retains account/cache data. The old routing flag becomes that note's event subscription. Business feedback embedded in historical cache rows is retained as migration input; the new provider does not author or interpret it. Existing key/runtime configuration is supplied explicitly through the local settings above. Stopping Worka is not a request to stop WeChat.

## Ordinary Agent operations

These are ordinary extension methods called through Worka with the host-derived note identity. There is no author setup hook or separate onboarding Agent.

| Method | Actual operation |
| --- | --- |
| `status` | Read-only local preflight and observed connection result. Does not install components, create configuration, start the reader, or prepare keys. |
| `prepare({ keyConfig? })` | Install the fixed runtime from the configured artifact, verify its archive and complete file receipt, and write private runtime configuration. An existing runtime is reused only when its receipt version matches the provider pin; an older version is upgraded to the pinned version. An optional existing key configuration is referenced, never copied. Missing keys return the recoverable `key_preparation_required` state. |
| `check({ chatId? })` | Execute reader status and one real, bounded timeline read. Join the calling note only after the read succeeds. Defaults to its existing selected chat or `filehelper`. |
| `initialize({ keyConfig?, chatId? })` | Prepare executable components and run the real check. If keys are missing, it asks for DSH's native user approval with the exact key file path and wxkey's verified local effects, runs the fixed bootstrap through the host-managed subprocess API, then checks the new config and performs a real bounded read. Repeating it preserves existing selections and subscriptions. |
| `sessions({ keyword?, offset? })` | Read a page of actual sessions for the joined account. |
| `select({ chats })` | Save this consumer's selected `{ id, name, type }` chats. Other consumers remain unchanged. |
| `read({ chatId })` / `refresh()` | Read selected messages with shared cursor/cache updates. Failed reads retain the previous cursor. |
| `enable({ enabled })` | Enable or disable this note's ongoing synchronization. |
| `events({ enabled })` | Subscribe this note to future `items.changed` notifications. Disabled by default. Enabling does not replay earlier messages. |
| `disconnect()` | Remove this note's subscription while preserving the account, runtime, keys, and other notes. |

Resources are `setup`, `connection`, `status`, `chats`, `messages`, `sessions`, and `events`, all under `extension.worka-wechat`. `setup` is a read-only resource name, not a lifecycle callback. `messages` takes `{ chatId }` and returns `{ chat, messages, updatedAt }`; its normal resource refresh performs ingestion separately from its read-only projection. `chats` returns this note's selected chats with cached counts/latest messages. `sessions` returns a page of `{ id, name, type }` items.

A note that requires this connection declares `prerequisites: [{ name: "extension.worka-wechat.status" }]` in `worka-note.json`. `ready` becomes true only after that authorized note joins following a real business read. The verification is tied to the local configuration fingerprint and persists across restart. A later transient read failure keeps that completed onboarding, exposes its `issue`, and sets `connected: false`; it does not force the user through onboarding again. An account/configuration change, missing executable/key configuration, or lack of note authorization keeps `ready: false`.

Each subscribed chat can produce an `items.changed` event with `itemId`, `chatId`, `title`, `messageId`, and `revision`. The notification identifies a changed source item; it does not ask an Agent to act on its own. Several changes awaiting delivery for one chat coalesce to its latest revision. A note decides which messages need business processing and maintains its own processing checkpoint and feedback. Host event keys make retried deliveries idempotent.

## First-use key preparation

`prepare` only installs the pinned runtime and never extracts keys. When `initialize` finds no valid key configuration, it uses the bundled wxkey v1.4.8 executable with the verified CLI `bootstrap --config <absolute path>`. Worka passes arguments directly through its managed subprocess API, not through a shell. It drains and discards stdout and stderr because diagnostics can contain local identifiers or key material. Bootstrap waits for an opened message database and verified keys for every existing message shard within the same bounded login session. Partial key capture never writes a successful setup configuration; unopened optional media and search databases do not block text initialization. After exit, the provider validates the local file without returning its contents, then performs the ordinary status check and one timeline read with a limit of one before joining the note.

Agent initiated bootstrap uses the existing DSH native `Caller.approve` flow. The approval shows the exact key file path and effects. Direct user invocation is the explicit initiation. The fixed release metadata pins the wxkey v1.4.8 module archive by SHA-256; the runtime receipt records the wxkey patch hash and executable hash. The current bootstrap signs its private copy for same-user debugging and requests only a read task port. It runs the existing native scan and database HMAC verification without administrator authentication or a debugger fallback. SIP and other system security settings stay unchanged.

wxkey scopes its process checks to the invoking macOS UID. A WeChat process belonging to another account at the shared `/Applications/WeChat.app` is left alone. For the invoking account, multiple instances, an unknown path or owner, or an already-running shadow copy stop preparation. Immediately before signaling, wxkey rechecks the PID, UID, executable path, and process start time to guard against PID reuse. It sends only `SIGTERM` to a verified process in the current account's original or shadow app; it does not use global `killall` or send `SIGKILL` to WeChat.

For the official Hardened Runtime app, wxkey copies `/Applications/WeChat.app` to `Library/Application Support/wx-mcp/WeChat-shadow.app` under the parent directory of its absolute `--config` path, ad-hoc signs only that copy, gives its main executable the local development `com.apple.security.get-task-allow` entitlement, and launches it for the read-only key scan. Nested helpers retain their ordinary ad-hoc signature. You may need to log in to that copy and confirm on your phone. Cleanup closes only the verified shadow process and reopens the original app only if the invoking account's original was running before bootstrap. Existing shadow directories are first preserved beside that path. If ownership or process state cannot be verified, wxkey stops without sending a signal and reports that manual recovery is needed. The supported build disables the command that resigns the shared `/Applications/WeChat.app`; it does not modify that original app or change SIP or other system security settings.

The absolute `--config` path owns both bootstrap storage and its shadow copy; it is carried unchanged through setup/image-key children. All bootstrap work stays under the invoking user. The real user home remains the source of account discovery. The new key configuration is written to the path shown in the approval. wxkey creates it through a temporary file with mode `0600`, syncs it, and atomically renames it. The key is persistent local sensitive state. An existing valid key configuration is never overwritten. A file that merely exists is insufficient: it must pass structure checks and the real read. Shutdown cancels only the Worka-managed wxkey process handle and confirms its exit before closing the provider.

New installation metadata lives in the current Worka profile. `WORKA_WECHAT_RUNTIME_CONFIG`, `WORKA_WECHAT_KEY_CONFIG`, `WORKA_WECHAT_RUNTIME_URL`, and `WORKA_WECHAT_RUNTIME_ARCHIVE` are explicit local overrides. The old runtime must be selected by its actual absolute path; it is not automatically discovered. Keys and message data are never packaged with the provider.

## Runtime provenance and diagnostics

`runtime/release.json` pins the macOS runtime version, platform, adjacent archive name, size and SHA-256. When an official asset has been published, it may also pin its exact release URL. Provider and Worka builds verify a local build cache or a checked-in adjacent archive before fetching such a pinned URL; they place the verified archive beside the packaged provider. First `prepare` automatically uses that adjacent archive and verifies its fixed SHA-256 and per-file receipt before installation. `runtimeUrl` and `runtimeArchive` remain optional deployment overrides and take precedence over automatic discovery. `runtime/sources.json`, `runtime/build-toolchains.json`, and the patch files record the pinned upstream MCP reader, wechat-cli, wxkey, standalone Python, SQLCipher inputs and the exact source changes/toolchains.

To build the patched runtime on macOS arm64, run `bun providers/wechat/runtime/build.mjs`. The recipe fetches Go 1.26.5 from the pinned official archive and verifies both the archive SHA-256 and extracted compiler binary SHA-256, fetches each upstream source archive from its pinned URL and verifies its SHA-256, installs Python dependencies with `--require-hashes`, applies the three wxkey patches, runs the selected source tests, and builds the runtime with Go 1.26.5 and Apple Swift 6.2.4. It writes the archive to `.tmp/wechat-runtime-cache/wechat-runtime-darwin-arm64.tar.gz` and updates `runtime/release.json` with the resulting exact size and hash. `WORKA_GO_BINARY` may select the same hash-matched Go compiler at another local path. No public URL is written for this local unpublished build. A clean checkout needs either the verified cache asset or an official asset with an exact URL in release metadata. The receiver needs no separate Python or Go installation. The fixed archive's mere existence is not a successful account check.

The reader is a DSH-managed local child under a network-denying sandbox. Its bridge admits only `status`, `sessions`, `timeline`, and `read_events`, sets the upstream strict-read-only flag, and disables media extraction, OCR, file text, voice and network features. Runtime/setup failures retain their operation and error code. Upstream diagnostic text can contain message bodies or keys; the bridge returns the actual exception class, errno or upstream error code and operation instead of dumping that text into logs.

Failed wxkey bootstrap status retains only fixed stage and failure enums, whether the host returned a child handle, an allow-listed OS error code, and a bounded exit code or known signal. The provider never stores command arguments, environment, paths, stdout, stderr, or arbitrary exception text in this diagnostic.

Cancellation and shutdown reclaim only the installer or reader handle returned by the host subprocess API. They request `SIGTERM`, wait up to 1.5 seconds for confirmed exit, then request `SIGKILL` and wait another 1.5 seconds. No process discovery or application-wide signal is used. If exit is still unconfirmed, cleanup reports `process_cleanup_failed` and closing fails; background timeout or protocol cleanup cannot silently count as successful. Closing also drains accepted starts and installations, including a child handle that arrives after cancellation. A failed startup retires its reader before a retry can launch another one.

## Acceptance boundary

Unit tests use isolated state directories, injected readers and synthetic messages. They verify sharing, independent consumer pause, first-read failure, preservation of a completed verification on transient failure, cursor persistence, old-provider coexistence, read-only key preflight, explicit runtime reuse, native approval ordering, the pinned bootstrap argument/environment set, safe output redaction, post-bootstrap inspection, and managed bootstrap cancellation. Fixtures do not launch wxkey or extract real keys. Real acceptance still requires user approval, the actual WeChat login/mobile confirmation if requested, one real bounded read, a second note reusing the connection, independent pause, and restart.

## Independent build

Run `bun run build` from this source directory after installing its development dependencies and the `@realiz3r/worka` peer. Inside the Worka repository, build Worka's public host declarations first. The build reads the peer package's public `exports["./host"].types` entry; it does not compile against Worka's internal source paths or another provider.

The build emits `dist/index.js` with only Node built-ins and `@realiz3r/worka/host` as runtime imports, plus the public TypeScript declarations. The source package manifest points to that `dist` entry. The generated `dist/package.json` instead points to its own adjacent `index.js` and `index.d.ts`, so the entire generated `dist` directory can be moved as a standalone compiled package with an installed Worka peer. It includes `runtime/`, `bridge/`, `README.md`, `LICENSE`, `NOTICE`, and `cordis.patch.yml`; no file depends on its original repository location. Generated output is not committed as implementation source.

The package exposes the ordinary DSH `name`, `inject`, and `apply` entrypoints. Its `dsh.bundle.patch` selects `cordis.patch.yml`, which mounts `@realiz3r/worka-provider-wechat` with the injected public `worka` host. `apply` registers the provider and gives DSH its asynchronous disposer. Use this standalone mount when the distribution has not already registered the built-in `worka-wechat` provider; two copies must not register the same extension name.

Building this package never downloads a runtime artifact, starts WeChat, extracts keys, or performs an account read. The runtime artifact is fetched by the Worka distribution build or first installation; first-use key preparation remains interactive and follows the effects described above. A Worka distribution that places this entry in `dist/providers/wechat` must use the relocated compiled manifest and keep the same adjacent assets and declarations.
